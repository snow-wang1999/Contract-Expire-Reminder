# 维保录入分析工具 · 大数据性能改造说明

单文件 `unified-warranty-analysis.html`，双击即用、离线、零依赖的形态保持不变。
判定规则和两个引擎（新签 / 续签）的代码都没有改，改的是外围的**数据管道、视图、导出、编排**四层。

## 实测对比

测试数据是一份真实批次（serviceLine 37 行、续保 SN 清单 2305 行、Agreement Barcode List 12.4 万行
（xlsx 25MB，解压后 sheet XML 411MB）、SublineList 4.8 万行），在 Chromium 中以 `file://` 打开测得。

| 环节 | 改造前 | 改造后 |
| --- | --- | --- |
| 导入 Barcode List（25MB / 12.4 万行） | 21.7 秒，**页面冻结最长 11.3 秒** | 5.5 秒（后台线程），主线程最长阻塞 0.09 秒 |
| 导入 SublineList（7.5MB / 4.8 万行） | 1.7 秒，冻结 0.5 秒 | 1.6 秒，不冻结 |
| 点击「开始分析」 | 13.3 秒，**冻结 12.8 秒** | 1.5 秒，分阶段显示进度（最长阻塞 0.9 秒） |
| 页面 DOM 节点数 | 224,746 | 1,593 |
| JS 堆内存 | 747 MB | 157 MB |
| 切换到 ② 级联判定 Tab | 5.4 秒 | 0.07 秒 |
| 导出 Excel | 14.7 秒，冻结 | 3.2 秒，页面不冻结 |
| 明细表可查看行数 | 前 20,000 行（之后截断） | 全量，并支持表内筛选 |
| **3 倍数据**（37 万行，sheet XML 1.2GB） | **浏览器标签页崩溃** | 导入 19.5 秒 / 分析 2.3 秒 / 导出 6.7 秒，堆 304 MB |

**结果一致性**：新旧两版跑 4 个场景（真实数据·续签、真实数据·新签、内置演示·新签、内置演示·续签），
`u_exportSheets()` 的全部结果行哈希完全相同；两版导出的 xlsx 逐单元格对比也完全相同。
此外用构造的边界文件（共享字符串富文本 / 注音、实体转义、布尔、缺省 `r` 属性、列空洞、
`<rowBreaks>`、绝对路径 rels、stored 压缩、带 BOM / 引号 / 换行的 CSV）对比，解析结果也完全一致。
不支持 Worker 时会回退到主线程分片解析，回退路径同样验证过结果一致。

## 原架构的瓶颈（逐项实测定位）

1. **Worker 实际上一直没有启用。** `new Worker("unified-worker.js")` 引用的外部脚本不随单文件分发，
   而且 Worker 里没有 `DOMParser`，旧解析代码在 Worker 中本来也跑不起来。结果所有解析都回退到主线程同步执行。
2. **整张 sheet 一次性解码成一个字符串。** 411MB 的 XML 一次 `TextDecoder.decode` 就要 11 秒，
   而且已经接近 V8 单个字符串的上限（约 512MB）。数据再大一点就直接失败（3 倍数据时标签页崩溃）。
   另外，每个单元格的值都是这个大字符串的切片（SlicedString），会把整块 XML 一直留在内存里。
3. **渲染。** 一次插入最多 2 万行的 `<table>`，4 个 Tab 同时渲染，22 万个 DOM 节点光布局就花了 10.9 秒。
4. **导出。** CRC32 按位计算（每字节循环 8 次），5.4 秒；整本工作簿拼成一个巨型字符串后再一次性编码，4.1 秒。

## 新架构

```
 ┌──────────────────────── 主线程（UI） ─────────────────────────┐
 │ 上传区 / 场景识别 ─▶ u_readRows ─▶ 引擎解析器(parseBarcode…)    │
 │                        ▲  rows: string[][]（接口与旧版同构）     │
 │                        │  按批解码（每批 4000 行，几毫秒）       │
 │ 分析编排 u_run：分阶段 + 让帧 + 进度  ─▶ 视图层：虚拟滚动表格   │
 │ 导出层：分块生成 XML → 查表 CRC32 → CompressionStream → Blob    │
 └────────────────────────┬─────────────────────────────────────┘
          postMessage(File) │ ▲ {dict 增量, cells: Int32Array}（transfer，零拷贝）
 ┌────────────────────────▼─┴── 解析 Worker（Blob URL 内联，每文件一个，最多 3 个并行）──┐
 │ Blob.slice 读 ZIP 中央目录（只读文件尾部）                                            │
 │ → Blob.slice(条目).stream() → DecompressionStream("deflate-raw")                     │
 │ → TextDecoder(stream) → 增量行扫描（内存只保留未闭合的行尾，O(块大小)）               │
 │ → 字符串字典：同值只存一份，新值复制一份断开大串引用 → [n,id…] 写入 Int32Array        │
 └───────────────────────────────────────────────────────────────────────────────────┘
```

### 1. 数据管道层（`XLSX_CORE` / `u_readRows`）
- **自包含内核**：`XLSX_CORE` 不引用任何外部变量，用 `Function.toString()` 拼成 Blob URL 来启动 Worker，
  双击 `file://` 打开时也能用。浏览器不支持 Worker 时，同一份代码在主线程按 30ms 时间片运行。
- **全程流式**：ZIP 条目按需切片读取，解压和解码都是流式的，按约 512KB 一块增量扫描。
  已经没有「整张 sheet 一个字符串」这一步，所以不再受字符串长度上限的约束。
  workbook.xml 和 rels 改用正则解析（Worker 里没有 DOMParser）。
- **字典编码传输**：数据从 Worker 回到主线程用的是字典增量加 Int32Array（可 transfer）。主线程按批还原成
  `string[][]`，接口和旧版 `readWorkbook` 完全一样，上层解析器和引擎都不用改。
  重复值（COA、日期、服务包等）只存一份，堆内存从 747MB 降到 157MB。
- **每个文件一个短命 Worker**：解析完立即 `terminate`，Worker 用过的内存马上全部释放。
  多个文件可以并行解析（最多 3 个）。

### 2. 视图层（`u_table` / 虚拟滚动）
- `u_table(headers, rows, rowCls)` 的签名不变。300 行以内仍输出原来的静态表格，外观不变。
  超过 300 行改为虚拟滚动：固定行高，只渲染可视区约 40 行，DOM 规模和数据量无关。
- 新增 `u_lazy(arr, fn)` 惰性行源：12 万行明细只为可见行生成单元格 HTML，不再预先构造 12 万个对象。
- 占位 div 由 `MutationObserver` 自动挂载，所有渲染函数仍然用 `innerHTML` 拼接，不用改。
- 每张大表自带表内筛选：首次筛选时分片建立纯文本索引，不阻塞页面。
- 实际录入比对表的「每页 1000 行 + 显示更多 + 上限 2 万」改为整个筛选桶直接虚拟滚动。

### 3. 导出层（`u_buildXlsxBlob`）
- 每 2000 行左右生成一块 XML（输出与旧实现逐字节一致），分块编码、增量计算 CRC32（查表法），
  边生成边写入 `CompressionStream`，压缩由浏览器在原生线程完成。最后用 Blob 拼装，块与块之间让出主线程。
- 写出前会剔除 XML 1.0 不允许的控制字符（旧版遇到这类字符会导出 Excel 打不开的文件）。
- 导出期间按钮显示进度，并防止重复点击。

### 4. 编排层（`u_run`）
- 改为 async 分阶段执行：级联判定、实际录入比对、渲染，阶段之间让出一帧，按钮上显示当前阶段，防止重复点击。
- `u_buildQuoteVs` 合并报价行时，原来用 `Array.find` 查找（O(n²)），改为 Map。

## 后续可选优化（目前不是瓶颈）
- 续签 / 新签引擎（`analyze` 约 0.8 秒、`u_buildCompare` 约 0.2 秒）仍在主线程同步执行。
  数据再大一个数量级时，可以考虑把「数据常驻 Worker、主线程只拿视图切片」作为下一步。
  这需要把两个引擎从 DOM 宿主里拆出来，改动面较大，这次没有做。
- 解析 Worker 内的耗时：解压加解码约 3 秒（浏览器原生），行扫描约 3–5 秒。如果需要还可以改为按列裁剪，
  只解码引擎会用到的列。

## 回归 / 基准脚本（`tools/`）
需要 Node 和 Playwright（Chromium）。数据文件不入库。
- `bench.js <html> <数据目录> [out.json]`：各环节耗时、主线程 long task、DOM 节点数、堆内存、导出耗时。设置 `NOWORKER=1` 可测主线程回退路径。
- `regress.js <html> <数据目录> <输出前缀>`：4 个场景的结果哈希，并保存导出的 xlsx（`ONLY=` 可选场景）。
- `cmpxlsx.py <目录> <场景…>`：新旧两版导出的 xlsx 逐单元格对比。
- `mkedge.py` / `eqedge.js`：构造边界 xlsx / csv，对比新旧解析结果。
- `mkbig.py <源 xlsx> <目标> <倍数>`：生成 N 倍规模的压力测试文件。
